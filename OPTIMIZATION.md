# Optimization: memory pressure, draw distance and request quotas

Порт пункта **Optimization** из анализа `libblackrussia-client.so`
(`PUNCT ANALYSE/optimization`, главы 01–09, 17, 21).

В клиенте нет «пресета качества графики». Есть **система реакции на давление
памяти**: она выбирает бюджет под объём ОЗУ, считает долю занятого бюджета,
держит автомат режимов с гистерезисом и задержками и из него управляет
дальностью прорисовки, квотами подгрузки и числом сохранённых моделей.

```
/proc/meminfo  ->  бюджет по ОЗУ (180 / 256 / 320 / 384 МБ)
остаток бюджета ->  автомат: normal / mitigation / critical
автомат        ->  масштаб дистанции (1.0 / 0.75 / 0.6), плавно 0.25 в секунду
давление       ->  квота запросов модели за кадр (3/5 против 1/2)
```

## Что где лежит

| файл | роль |
|---|---|
| `src/extras/custom/OptimizationProfile.h` | **чистая логика**: 48 параметров, разбор секций, бюджет, давление, автомат. Без движка — тестируется на хосте. |
| `src/extras/custom/Optimization.cpp` | обвязка: `/proc/meminfo`, чтение `data/optimization.json`, запись масштаба в `CRenderer::ms_lodDistScale` |
| `src/extras/custom/MiniJson.h` | общий JSON-ридер (используется также `CustomTimecycle.cpp`) |
| `gamefiles/data/optimization.json` | конфиг по умолчанию: все 48 ключей с дефолтами клиента |
| `tests/OptimizationProfileTests.cpp` | хостовый тест: вся таблица дефолтов, частичный конфиг, мусор, бюджет, давление, автомат, гистерезис, независимость от Гц |

## Таблица параметров (глава 8)

| секция | параметров | ключевые значения по умолчанию |
|---|---|---|
| `memoryPressure` | 5 | вход 32 / выход 48 МБ, критический 8 / 24 МБ, порог давления 0.75 |
| `worldDistance` | 6 | масштабы 0.75 / 0.6, скорость 0.25 в секунду, задержки 1000 / 3000 мс, запас дальней плоскости 1.05 |
| `networkVehicles` | 13 | выгрузка 35/25 м, агрессивно 20/15 м, защищено 20 м, батчи 2–8, квота 3 (1) |
| `remotePlayerAppearance` | 16 | аксессуары 20/15 м, скины 30/25 м, сохранять до 30 м, защита 12/20 м |
| `asyncModelRequests` | 8 | квота 5 (2), таймаут 10 с, до 150 запросов, повтор 100 мс × 2^k до 2000 мс |

Каждый ключ необязателен: отсутствующий остаётся с дефолтом. Файл может быть
частичным — это поддерживается намеренно, как и в клиенте (глава 02, §2.3).

## Почему это лучше прежней эвристики

До порта в `CStreaming::Update` стояла проверка свободной памяти устройства:

```c
if (availMB < 280)      targetScale = 0.60f;
else if (availMB < 450) targetScale = 0.75f;
else                    targetScale = 1.00f;   // мгновенный переход
```

Три проблемы, каждая из которых приводила к видимой «немощности» картинки:

1. **Сравнивалась не та величина.** Свободная память телефона не связана с
   бюджетом стриминга: на устройстве с 8 ГБ при 600 МБ свободных игра всё равно
   считала, что «места полно», и держала полную дальность до OOM.
   В клиенте давление — это доля занятого *бюджета*, и считается она по
   дизассемблеру `0xe582b4`, а не по сводке главы:

   ```
   знаменатель = предел - (база + зарезервировано)
   числитель   = max(занято - база, 0) + резерв
   ```

   Обратите внимание: **резерв стоит в числителе**, а не в знаменателе —
   текст главы 09 пересказывает формулу неточно, точная берётся из кода.
   Бюджет при этом берётся из ОЗУ.
2. **Переход мгновенный.** Дальность прыгала на 25–40 % за один кадр; в клиенте
   множитель идёт со скоростью `distanceScaleChangePerSecond` (0.25/с) и только
   после `mitigationDelayMs` (1 с), а возврат — после `recoveryDelayMs` (3 с).
3. **Не было гистерезиса.** Один порог = дребезг на границе (выгрузка модели
   каждый кадр). Теперь у каждого режима пара порогов: 32/48 и 8/24 МБ.

Дополнительно квота запросов за кадр теперь берётся из того же автомата
(3 → 1 и 5 → 2), а цель кольцевого буфера машин снижается мягко: 100 / 80 / 60 %
от обычной. Делители `preservedPlayers*` к машинам **не** применяются — это
разные наборы; для игроков реализована ровно та форма, которую подтверждает
глава 04, §4.2: `max(minimumPreservedPlayers, всего / divisor)`, где в тяжёлом
режиме берётся `severePreservedPlayersDivisor`. Числовые значения и формулу
батча архив прямо называет неподтверждёнными, поэтому процентов мы не выдумываем.

4. **Выгрузка была не порционной.** `MakeSpaceFor` крутил `RemoveLeastUsedModel`,
   пока тот не вернёт `false`, то есть одна загрузка могла просканировать весь
   загруженный список внутри одного кадра. Глава 07, §7.5 прямо говорит, что
   выгрузка в клиенте порционная (`cleanupChecksPerFrame`) — именно против
   фризов, а не ради среднего FPS. Теперь бюджет проверок берётся из профиля
   и уменьшается под давлением; когда он исчерпан, объекты за камерой всё равно
   освобождаются, а модель остаётся запрошенной до следующего кадра.

5. **Смягчение было невидимым на низком ползунке дальности.** Множитель
   зажимался абсолютным полом `DRAWDIST_MIN = 0.80`. Если игрок держал
   ползунок на минимуме (обычное дело на телефоне), критический масштаб 0.60
   просил 0.48, а кламп возвращал 0.80 — то есть оптимизация не давала
   **ничего**. Теперь кламп относительный: ползунок ограничен своим
   диапазоном, а ступень оптимизации умножает ниже его пола. На минимуме
   ползунка смягчение — это −25 %, критический режим — −40 %, а не 0 %.

## Что применяется

| параметр | куда идёт |
|---|---|
| `mitigation*/critical*DistanceScale` | `CRenderer::ms_lodDistScale` через `EffectiveDrawDistanceScale()`: ползунок меню ограничен своим диапазоном, ступень оптимизации умножает ниже его пола (иначе минимум ползунка съедал всё смягчение) |
| `farPlaneMarginScale` | `RwCameraSetFarClipPlane` в `main.cpp`: `max(FarClip, 600 · scale · margin)` |
| `vehicle/asyncRequestsPerFrame` | квота загрузок в `LoadRequestedModels` на Android |
| режим (normal/mitigation/critical) | `desiredNumVehiclesLoaded`: 100 / 80 / 60 % от обычной цели (политика reVC, не число из клиента) |
| `minimumPreservedPlayers` / `preservedPlayersDivisor` / `severePreservedPlayersDivisor` | `Controller::PreservedPlayerCount()` — `max(min, всего / divisor)`, тяжёлая ветка на `severe…Divisor` |
| `cleanupChecksPerFrame` | бюджет проверок при выгрузке в `MakeSpaceFor`: 100 по умолчанию, 3/4 в смягчении, половина в критическом, но не меньше одной |
| предел обхода мира | `WORLD_WALK_MAX_ENTITIES = 2000` (`0x7d0`) в `AddModelsToRequestList`; кольцо — `WORLD_WALK_RING_SLOTS = 512` (`0x200`) |
| `projectedPressureThrottle` | выбор обычной/стеснённой квоты |
| остальные дистанции | прочитаны, провалидированы и доступны через `revcopt::Current()`; потребителя в одиночной игре у них нет (глава 09, §9.6: в клиенте их тоже читает только валидатор) |

## Коллизии

В архиве **нет параметров коллизий**: всё, что там есть по этой подсистеме —
загрузчик формата `LoadCollisionFile` (`0xe06aac`, 333 инструкции, единственный
ассерт `colVersion.has_value()`) и `GetColModel` с проверкой `COL IS NOT FOUND!
MODEL %d` (`0xe876a0`, 147 инструкций). Это разбор `.col`, а не настройки. Поэтому
пункт закрыт исправлениями в собственной реализации порта, а не переносом чисел.

1. **Обход миссионных сущностей был внутри цикла слотов.** `CColStore::LoadCollision`
   гонял полный `MAX_CLEANUP` (50 итераций, в каждой — поиск в пуле машин или
   педов) внутри цикла по всем 31 слотам. Это до 1550 итераций и до 1550
   поисков в пуле **на вызов**, а вызов идёт каждый кадр из `CStreaming::Update`
   и ещё раз из `CCollision::SortOutCollisionAfterLoad`. Список теперь читается
   один раз до цикла, а в свободной игре не читается вовсе: `CMissionCleanup`
   уже ведёт счётчик `m_nCount`, и он равен нулю.

2. **`EnsureCollisionIsInMemory` блокировал кадр по разу на слот.** Внутри цикла
   стояли `CTimer::Suspend()` + `LoadAllRequestedModels()` — по одному на каждый
   незагруженный слот в радиусе. Один `LoadAllRequestedModels` забирает весь
   список запросов, поэтому теперь сначала ставятся в очередь все слоты радиуса,
   затем одна блокировка.

3. **Политика отбора слотов вынесена в `ColSlotSelection.h`** и покрыта тестом.
   Отрицательные отступы (`-119`, `-80`, `-110`, `-115`) — это не опечатка:
   `CRect::IsPointInside(p, radius)` **сужает** бокс на `radius`, то есть слот
   считается нужным, только когда точка уже настолько внутри. Это гистерезис
   загрузки/выгрузки; «исправление» знаков на плюс вернуло бы дребезг на границе.

Проверено: `tests/ColSlotSelectionTests.cpp` — 9 групп утверждений, включая то,
что отступы именно сужают бокс, и что слот `yacht` держится всегда.

### Коллизии: соответствие формату и пределам

Аудит по десяти главам разбора (`collisions/Анализ/`) дал четыре дефекта,
которые видны в игре, а не только в коде.

1. **Несколько моделей в одном файле терялись.** И `.col`-записи, и `.cls`-чанки
   (`CLST`/`CLSF`) индексировались обходом «пока следующий байт — тег». В
   реальном файле между записями бывает нулевое выравнивание, а запись в IMG —
   это срез, округлённый до 2048-байтных секторов, то есть с нулевым хвостом.
   Обход спотыкался на первом же таком байте и **прекращался**: все модели после
   первого промежутка отбрасывались молча. На Android вдобавок ненулевой счётчик
   ошибок означал «это legacy-файл», и `.cls` разбирался второй раз другим
   путём. Теперь нулевые промежутки пропускаются, а мусор по-прежнему считается
   ошибкой. Покрыто `tests/CollisionContainerTests.cpp`.
2. **Размер записи не проверялся.** `LoadCollisionFile` читал `modelsize` из
   потока и копировал `modelsize-24` байт. Запись короче собственного 24-байтного
   имени давала отрицательную длину, и копирование затирало модель мусором;
   запись длиннее буфера читала за его концом. В отдельном пути
   `LoadCollisionFile(filename, slot)` размер вообще шёл в `fread` в глобальный
   буфер на 55 000 Б без проверки. Оба места теперь останавливают обход.
3. **Пределы не совпадали с клиентом.** Ассерты клиента дают **129** сфер
   (`0x81`), **1600** треугольников (`0x640`) и **101** бокс (`0x65`); в порте
   стояли 128, 600 и 32. Два последствия. Модель, у которой сфера-охват задевает
   от 600 до 1600 треугольников, обрезала список кандидатов — попадания терялись.
   Хуже с боксами: в реальной карте **510** моделей имеют больше 32 боксов (до
   274), и у них проверялась только первая треть. Ассерты, которые это поймали
   бы, в релизе не собраны. Пределы вынесены в `src/collision/ColLimits.h`,
   копирующие циклы живой (не VU) ветки ограничены явно. Покрыто
   `tests/CollisionCountLimitsTests.cpp`.

   **Отдельно про счётчики из файла — это был мой дефект, найденный по логу.**
   Первая версия обрезала счётчики секций до этих пределов. Так делать нельзя:
   счётчик задаёт, на сколько сдвинется указатель чтения, поэтому обрезка сдвигает
   **все следующие** секции. У модели с 48 боксами читалось 32, счётчик вершин
   попадал на данные боксов, выходил отрицательным и обнулялся, а счётчик
   треугольников оставался положительным — модель получала треугольники,
   ссылающиеся на невыделенный массив вершин, и падала в `CalculateTrianglePlanes`
   ещё на экране загрузки. Теперь счётчики читаются ровно как в клиенте
   (`ldrsh`), а проверяется только то, что секция помещается в реальный размер
   записи; первая не поместившаяся секция прекращает чтение. Дополнительно список
   треугольников сбрасывается, если у него нет вершин или индекс выходит за
   последнюю вершину.
4. **Переполнение хранилища слотов теряло файлы.** `AddColSlot` разыменовывал
   результат пула после `assert`. При 31 слоте и кастомной карте с большим числом
   `.col` файлы за пределом оставались без коллизии — сквозь объекты можно
   проходить. Теперь занятость проверяется до добавления, а количество
   сообщается в сводке IMG так же, как для TXD.

Открытым остаётся порядок min/max в bbox для тегов с флагом версии 1
(`CLSF`/`CLST`/`BOLL`): §2.7 говорит «обратный ход», но ни смещения, ни
подтверждающий образец в наборе не приведены, поэтому конвертер не менялся.

## Тест

```bash
g++ -std=c++11 -O1 -o /tmp/optp tests/OptimizationProfileTests.cpp -Isrc/extras/custom
/tmp/optp    # optimization profile tests passed

g++ -std=c++11 -O1 -o /tmp/cols tests/ColSlotSelectionTests.cpp -Isrc -Isrc/math -Isrc/collision
/tmp/cols    # col slot selection ok
```

Проверяется в том числе то, что легко сломать:

* все 48 дефолтов и порядок секций;
* частичный конфиг не сбрасывает остальные поля;
* битый/глубоко вложенный JSON отвергается без переполнения стека;
* нулевой масштаб дистанции и перевёрнутые пороги зажимаются `Sanitize()`;
* режим не переключается между 32 и 48 МБ ни в одну сторону (500 кадров);
* сглаживание по времени, а не по кадрам: 60 и 30 Гц приходят в одну точку.

## Границы

* Бюджет стриминга в reVC не выделяется физически: `ms_memoryAvailable`
  включён только под `USE_CUSTOM_ALLOCATOR`, поэтому величина бюджета — это
  цель для эвристики, а не жёсткий лимит. Давление считается от свободной
  памяти устройства относительно бюджета; недоступный `/proc` даёт
  консервативное «полное давление», а не «места полно».
* Пары дистанций для машин и внешности игроков в одиночной игре не имеют
  потребителя — ровно как в клиенте, где это доказано тремя методами
  (глава 09, §9.6). Они остаются в конфиге, чтобы файл был совместим.
* Цена кадра статически не измеряется: горячие пути (`render`/`stream`)
  требуют профайлера на устройстве (глава 07, §7.4).
