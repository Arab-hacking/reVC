# Загрузка ресурсов из папки `custom` в рантайме (`.mod` / `.dff` / `.btx` / `.cls` / `.ifp` / `.ani`)

Документ описывает переделку reVC, после которой игра **сама**, прямо во время работы,
читает контейнеры Black Russia (`.mod`, `.btx`, `.cls`), обычные RenderWare-модели
(`.dff`) и анимационные словари (включая SA `.ifp`/`.ani`) из папки `custom` и её zip-архивов.

Ключевые требования, которые выполнены:

* никакой внешней конвертации — ни `brconv`, ни `brmod.asi` не нужны;
* **никаких временных файлов на диске** — архив распаковывается в память, конвертация
  идёт в памяти, готовый объект сразу отдаётся движку;
* файлы моделей, текстур и коллизий из `custom` имеют приоритет над IMG-архивами игры
  и файлами в папке игры; **VC-анимации — исключение**: для них всегда берётся IFP игры;
* поддерживаются модели (`.mod` и `.dff`), текстуры (`.btx`), коллизии (`.cls`) и
  SA/BR-анимации (`.ifp`/`.ani`: `ANP2`/`ANP3`);
* SA-совместимые ped DFF получают отдельный SA animation bank; нативные VC-модели
  продолжают использовать оригинальные VC-анимации;
* **`.mod` читается нативно**: содержимое архива и есть поток RenderWare — расшифровка
  TEA и починка заголовка идут прямо в буфере, отдельный `.dff` нигде не создаётся
  (ни на диске, ни отдельным файлом в памяти).

---

## 1. Как включить и куда класть файлы

```c
// src/core/config.h
#define CUSTOM_MODELS                  // сама поддержка
#define CUSTOM_MODELS_FOLDER "custom"  // имя папки в корне игры
```

Архивы кладутся в `<папка игры>/custom/*.zip` (можно в подпапки, до 8 уровней вложенности).
Для `.mod`/`.btx`/обычных ресурсов используется имя файла без пути; для новых `.ide`/`.ipl`
важен **полный относительный путь** — подробнее в разделе «Карты BR» ниже.

Пример:

```
GTA Vice City/
  custom/
    cars.zip          -> glendale.mod, glendale/body.btx, glendale/wheel.btx, ...
    map_pack_1.zip    -> ...
    map_pack_2.zip/   (в подпапке тоже можно)
```

Папку можно переопределить переменной окружения `REVC_CUSTOM_DIR` (полезно, когда архивы
лежат вне папки игры).

**Лог.** Без дополнительных переменных создаётся один `debug.log` рядом с игрой:
запуск, скан папки `custom`, загрузка IMG/TXD/IFP, конвертация и причины отказов.
На macOS и Android файл находится в каталоге пользовательских данных/`STORAGE_ROOT`.
Отдельного `custom_models.log` больше нет; `REVC_CUSTOM_LOG` не требуется.

## 2. Правила имён

Игра запрашивает свои файлы **по именам из `IDE`/`vehicles.ide`/`default.ide`**, поэтому
файлы в архиве должны называться так же:

| файл в архиве        | что это                                                     |
|----------------------|-------------------------------------------------------------|
| `<имя модели>.mod`   | BR-модель; имя = имя модели из IDE (например `glendale.mod`)    |
| `<имя модели>.dff`   | обычный RenderWare DFF; для игрока поддерживается `player.dff` после строгой проверки clump |
| `<имя текстуры>.btx` | одна текстура; имя = имя текстуры, которое упоминает модель  |
| `<имя коллизии>.cls` | одиночная коллизия; в `br_collision.zip` файл может содержать сотни моделей с собственными внутренними именами |
| `<имя>.ifp`          | SA/BR-анимации (`ANP2`/`ANP3`) только для SA-скелетов; имя = запрашиваемый словарь, обычно `ped` |
| `<имя>.ani`          | ANP3 (IFP v2); заголовок SA mobile читается без перестановки |

Для SA-модели игрока кладите настоящий `player.dff` (и его `.txd`/`.btx` текстуры) в
`custom` или архив. Он принимается только если корневой RenderWare-объект — clump с
геометрией, прошедшей проверку; повреждённый файл оставляет игровую модель на месте.
`player.mod` намеренно остаётся запрещённым: некоторые common-архивы содержат под этим
именем маленькую заглушку, небезопасную для загрузчика.

Регистр не важен, расширение тоже (`Glendale.MOD` найдётся). Дополнительно `.btx`
длиннее 31 символа индексируется и по первым 31 символам — RenderWare хранит имя
текстуры в `char[32]`, поэтому модель всё равно ссылается на укороченное имя.

Имя TXD-слота **не обязано** совпадать с именем модели (в VC так у `hotdog`/`hotdog1`):
если под именем запрошенного словаря в архивах ничего нет, загрузчик ищет модель, которой
этот словарь принадлежит, и собирает текстуры по списку из неё. Поэтому текстуры
подхватываются и в этом случае, хотя файлы `.btx` называются именами текстур, а не TXD.

Анимационный словарь запрашивается по имени блока, например `ANIM\\PED.IFP`. Положите
SA/BR `ped.ifp` или `ped.ani` в `<папка игры>/custom/` либо в ZIP внутри этой папки.
Это **не** `MODELS/CUSTOM.IMG`. Компактный `ANP2`/`ANP3` загружается в отдельный
банк `sa_ped` только для SA-скелетов. VC-скелеты всегда используют штатный IFP
из игры. `ANPK` из `custom` теперь игнорируется и не может заменить VC-анимации;
недостающий SA-клип никогда не заменяется клипом VC (и наоборот).

Для **подмены** штатной модели (например, `glendale.mod`) её имя должно существовать
в игровой IDE. Дополнительные **статические объекты карты** теперь регистрируются
из IDE внутри `common.zip`/`custom`, описанных ниже; автомобили по-прежнему требуют
игровой IDE и `handling.cfg`. Загрузчик выбирает обработчик по **типу записи IDE**:
автомобиль — vehicle, ped — ped, статический объект — atomic. Для ped/vehicle
проверяются root frame, геометрия, а для SA-педа — skin и совместимая иерархия
костей **до** установки clump. Если подменный DFF несовместим, причина пишется в
`debug.log`, загрузка отклоняется и повторные попытки чтения этой же подмены в
текущем сеансе прекращаются; при наличии исходной модели будет испробован
штатный поток. Это не делает повреждённый DFF пригодным для игры.

Если имя встречается в нескольких архивах, побеждает **архив с более свежей датой
изменения** (так же решает и оффлайновый `brconv`).

## 3. Что происходит при загрузке

Общая схема для любого запрошенного игрой файла (модель, TXD, коллизия):

1. `CStreamingInfo::GetCdPosnAndSize` — загрузка идёт для **всех** файлов из `custom`, а
   для тех, которых нет ни в одном IMG игры, дополнительно выдаётся «позиция в образе»
   размером в один сектор. Это единственная уступка потоковой системе: она обязана знать,
   откуда файл читать, иначе пометит запрос как «пустой файл» и выбросит его
   (`GetNextFileOnCd`). Читать по этой позиции ничего не нужно (2 КБ мусора из начала
   образа, они выбрасываются), а так как к такому файлу ничего не прицеплено цепочкой
   `m_nextID`, он всегда оказывается в канале один и не может испортить чтение соседних
   файлов. Файлы, которые в IMG есть, сохраняют **свою настоящую позицию и размер** — так
   не нарушается склейка «читаем до 4 соседних файлов за один запрос». В итоге файл ведёт
   себя как обычный: очередь, канал, `ms_memoryUsed`, слоты TXD/COL, списки загруженных
   моделей — всё штатное, и работают даже файлы, которых в игре нет вообще.
2. `CStreaming::ConvertBufferToObject` — здесь буфер из образа игнорируется,
   вызывается `CStreaming::LoadCustomFile`, который повторяет всё, что делает обычная
   загрузка: берёт ссылки на TXD и анимации, ставит текущий TXD, обновляет список машин,
   переводит стриминговую запись в `LOADED` и учитывает память.
3. `CCustomModels::Load` — распаковка записи архива в память и **прямая передача
   движку стандартными путями RenderWare**: `.mod` проходит `br::understandModInplace`
   (расшифровка и нормализация прямо в буфере), обычный `.dff` читается как есть;
   текстуры идут через `brtex::parseBtx`, коллизии — через `br::convertClsToCol`:
   * модель — буфер записи (уже приведённый к потоку RenderWare) открывается как
     `rwSTREAMMEMORY` и уходит в
     `CFileLoader::LoadAtomicFile` / `LoadClumpFile` / `StartLoadClumpFile+FinishLoadClumpFile`
     (ровно те же три ветки, что и в обычной загрузке);
   * текстуры — `RwRasterCreate` + `RwRasterLock` по каждому мипу (с учётом порядка
     байт D3D9/D3D8/Xbox — BGRA, OpenGL — RGBA), затем `RwTextureCreate`,
     `LINEARMIPLINEAR`, `WRAP`; текстуры кладутся в `RwTexDictionary` слота TXD;
   * коллизия — целиком в памяти: `br::convertClsToCol` приводит блоки `CLSF`/`CLST`/`COL2`/
     `COL3` к COL3, затем `customcol::ToGameFormat` (`CustomCol.cpp`) переводит его в формат
     **v1 `COLL`** — единственный, который читает VC, — и результат уходит в штатное хранилище
     коллизий игры: в слот (`CColStore::LoadCol`) или подменой одного блока внутри `.col`-файла
     (`CFileLoader::LoadCollisionFile`);
   * анимации — `CAnimManager::LoadSAAnimFileFromCustom` проверяет компактный
     `ANP3`/`ANP2` из `custom` и читает его в отдельный банк `sa_*` через
     `LoadAnimFile_ANP23` (включая сжатые кадры); штатный VC `ANPK` читается
     **только из игры**, независимо от наличия файла в `custom`. Стандартный BR
     `.ani` уже содержит ANP3. Для старого shim-варианта с лишним 4-байтным
     словом перед первым клипом оно удаляется после структурной проверки.

Ничего, кроме памяти, при этом не создаётся: файлы на диск не пишутся, внешние утилиты
не запускаются.

### Фоновая подготовка и повторная загрузка `.mod`/`.btx`

* `RequestModel` ставит в ограниченную очередь подготовку запрошенной модели **и её TXD**.
  Один рабочий поток читает отдельные записи ZIP (или loose-файлы), исправляет/проверяет
  `.mod`/`.dff`, определяет имена текстур, декодирует нужные `.btx` и запекает terrain
  **без вызовов RenderWare/GPU**. Очередь дедуплицирует источники, повышает приоритет
  важных запросов, ограничивает число заданий/готовых результатов (16/1), отменяет
  невостребованные задания и дожидается чтения архива при завершении игры. Готовые
  результаты попадают в кэши только на игровом потоке. Проверка `CanServe` не читает
  архив и не декодирует модель; обычный `GetNextFileOnCd` пропускает запрос до готовности
  его CPU-данных. **Только** явно блокирующий `LoadAllRequestedModels` ждёт поток; при
  недоступном потоке или превышении лимита возможна синхронная резервная загрузка.
* Подготовленный байтовый поток `.mod` (расшифровка, исправление RenderWare и проверка
  геометрии) хранится в LRU-кэше. Поиск имён текстур для TXD и реальная загрузка модели
  используют **один и тот же** неизменяемый буфер. При повторной загрузке после
  вытеснения не приходится вновь читать и расшифровывать `.mod` **пока он в кэше**;
  объект RenderWare при этом по-прежнему создаётся штатным загрузчиком, когда его
  снова запрашивает стриминг. Аналогично кэшируются байты обычного `.dff`.
* `.btx` парсится и декодируется в RGBA-миры один раз на время нахождения в
  CPU-кэше. Повторно используются также запечённые 512×512 терраин-текстуры;
  длинное имя и его сокращённый RW-вариант ссылаются на **один** источник. При
  вытеснении *потокового* custom TXD сам готовый словарь с GPU-растрами может
  временно остаться в отдельном LRU и при следующем запросе возвращается в тот
  же TXD-слот без декодирования, создания растра и повторной загрузки в GPU.
  Чужие/штатные TXD этот путь не кэширует; освобождённый слот не может получить
  словарь с прежним именем. Кэш GPU освобождается до выключения RenderWare.
  Если включить экспериментальный `USE_CUSTOM_ALLOCATOR`, сохранение GPU TXD
  отключается: иначе сохранённая память ошибочно учитывалась бы стримингом
  как занятая активными объектами. **Фоновый поток тоже выключен**: глобальный
  `CMemoryHeap` этого режима не потокобезопасен. CPU-кэши `.mod`/`.btx` остаются,
  но холодная подготовка идёт синхронно, как до оптимизации.
* Пределы кэшей **не изменились**: **64 МиБ** подготовленных моделей, **64 МиБ**
  декодированных текстур и **64 МиБ** *оценочного* размера сохранённых GPU TXD.
  При превышении лимита старые записи удаляются: «один раз» означает **пока запись
  остаётся в кэше**, а не навсегда за сессию. Крупная одиночная текстура может быть
  передана из потока на одну загрузку без помещения в LRU; память активных RW-объектов,
  временные буферы чтения/декодирования, служебные структуры и обычный стриминг
  **не входят** в эти пределы. Изменения файлов в `custom` подхватываются только
  после полного перезапуска приложения. В `debug.log` при завершении доступны
  `asset caches: ... hit / miss / evicted` и `background CPU: ...` с потолками кэшей.
* Это не мобильный GPU-пайплайн BR: для D3D9/GL3 `.btx` с ASTC по-прежнему
  декодируется в RGBA на CPU, но при штатном запросе — **до** загрузки объекта в
  фоновом потоке. Форматы ETC2/ASTC нельзя безопасно отправить на любую из этих
  платформ напрямую. RenderWare-объекты и GPU-растры создаются **только** в игровом
  потоке; за проход канала не объединяется более одного custom TXD/модели. Уже
  существующие дистанции LOD и `DeleteRwObjectsBehindCamera` не менялись: модели
  **удаляются** вне обзора, не закрепляются кэшем, а после возврата создаются снова.
  Загрузка целого `.txd`, коллизий и анимаций не переносилась в фоновый поток; низких
  `.tmb`-заглушек и форматов `.bpc` здесь нет. На первом показе остаются возможны
  расходы на RW/GPU, а при переполнении кэша — повторная подготовка.

## 4. Приоритет над файлами игры

Точки подключения — это все места, откуда игра берёт модели, текстуры и коллизии:

| функция                                        | что перехватывает                                    |
|------------------------------------------------|------------------------------------------------------|
| `CStreamingInfo::GetCdPosnAndSize`             | все потоковые файлы (модели, TXD, COL)                |
| `CStreaming::ConvertBufferToObject`            | собственно загрузка потокового файла                  |
| `CFileLoader::LoadTexDictionary`               | `.txd`, перечисленные в `gta_vc.dat` (`TEXDICTION`)   |
| `CFileLoader::LoadCollisionFile` (по имени)    | `.col`, перечисленные в `gta_vc.dat` (`COLFILE`)      |
| `CFileLoader::LoadClumpFile` (по имени)        | модели, перечисленные в `gta_vc.dat` (`HIERFILE`)     |
| `CAnimManager::LoadAnimFile`                   | анимационные словари `PED.IFP` и т.п.                 |

Для моделей, текстур и коллизий сначала спрашивается папка `custom`, и только если там
ничего нет — берётся файл игры. Для **анимаций** правило иное: штатный VC-словарь всегда
берётся из игры, а SA/BR-словарь из `custom` добавляется параллельно и используется только
SA-скелетами. Коллизия из `.cls` при этом подменяет **только свой блок** `.col`-файла
(по имени модели), остальные блоки файла читаются как обычно.

Порядок загрузки тоже остался ванильным: TXD грузится перед моделью (проверка
`TxdNotLoaded` в потоковом канале не тронута), поэтому текстуры модели гарантированно уже
в памяти, когда читается геометрия.

## 5. Поддерживаемые форматы (как в `brconv` v1.2)

* **`.dff`** — обычный поток RenderWare; перед передачей игре проверяются clump-root,
  геометрия и целостность заявленных данных. Для `player.dff` эта же строгая проверка
  обязательна в архивном и loose-file путях; `player.mod` остаётся запрещённым.
* **`.mod`** — заголовок `magic 0xAB921033` + TEA-шифрование (8 раундов, 15 вариантов
  ключа) + нормализация потока RenderWare до SA-вида — всё выполняется **на месте**,
  в том же буфере, который затем сразу читает движок (`br::understandModInplace`); внутри должен быть **clump**
  (в VC «простая» модель тоже хранится как clump с одним atomic). Если поток оказался не
  clump'ом (например, словарь UV-анимаций), файл не подменяется, и игра берёт своё.
* **`.btx`** — `u32 flags` + KTX11: ASTC (4x4 … 12x12, блок определяется по фактическому
  размеру первого мипа, у BR enum не совпадает с данными), а также несжатые RGBA8/RGB8/
  RGBA4444/RGB565/RGBA5551. NPOT-текстуры пересэмплируются в степень двойки (как в оффлайн
  конвертере — D3D9/RW этого требует).
* **`.cls`** — для BR `CLST`/`CLSF` с внутренним `CED2` используется отдельный
  проверяемый по смещениям путь `BrCollisionFormat.h` (включая много моделей в одном
  контейнере). Старые `.cls` с блоками `COL3`/`COL2`/`COLL` продолжают использовать
  два прежних этапа конвертации в памяти:
  1. `br::convertClsToCol` (как в `brconv`): `CLSF` переписывается из тела COL1 в COL3
     (сфера → центр+радиус, бокс без изменений, вершины в fixed-point int16/128, грани в
     uint16, выравнивание на 4); `CLST` приводится к COL3 с перестановкой границ; материалы
     > 178 сбрасываются в 0.
  2. `customcol::ToGameFormat` (`CustomCol.cpp`) переводит COL2/COL3 в **v1 `COLL`** —
     формат, который умеет читать только VC: границы (оба порядка следования
     «бокс-первый»/«сфера-первый» распознаются, при нечитаемости пересчитываются из
     геометрии), сферы `center,radius` → `radius,center`, вершины fixed-point → float,
     число вершин выводится как «максимальный индекс грани + 1» (в COL2/3 оно не хранится),
     грани с индексом ≥ числа вершин отбрасываются, лимиты 32767 вершин/граней, материалы
     > 34 (`SURFACE_CONCRETE_BEACH` — конец таблицы VC) сворачиваются в `SURFACE_DEFAULT`;
     готовые блоки `COLL` копируются без изменений.
* **`.ifp`** — анимационные словари двух видов: штатный VC `ANPK` и SA `ANP3`/`ANP2`.
  В SA-формате тип каждого кадра (`frameType` 1–4), а не дополнительное слово заголовка
  анимации, определяет fp32/i16-представление. Лимиты: 2500 анимаций и 180 блоков.
* **`.ani`** — тот же ANP3/IFP v2, что и `.ifp`: мобильная шапка содержит магию,
  имя блока (24 байта), число анимаций и неиспользуемое `groupVal` (в том числе 0/1).
  Переставлять её нельзя. Если у прежнего shim-варианта есть лишнее слово
  перед первым клипом, оно удаляется только после проверки, что обычный ANP3
  не читается; после сдвига тело проверяется снова, сами кадры не меняются.
* **Терраин-слои**: если модель ссылается на составную текстуру (маска + до 4 слоёв),
  она запекается в 512×512 (`brtex::bakeTerrain`), слои берутся из своих `.btx`.
* **Zip**: метод `store` и `deflate` (свой небольшой inflate внутри игры, без внешних
  библиотек), ZIP64 (архивы > 4 ГБ) — читается только центральный каталог, данные
  распаковываются по одной записи. Зашифрованные архивы и другие методы сжатия
  игнорируются.

## 6. Ограничения

* Максимальный размер одной записи в архиве — 64 МБ (защита от «сюрпризов»).
* Отдельная текстура, для которой нет модели с таким именем, тоже работает: если
  в архиве есть `.btx` с именем TXD-слота, слот собирается из него одного.
* Коллизия `.cls` применяется к слотам коллизий игры и к блокам `.col`-файлов. Машины в
  VC коллизию в `.col` не держат (она внутри DFF), поэтому `.cls` для машины
  использоваться не будет — это ограничение самой игры, а не загрузчика.
* Для SA/BR `ANP2`/`ANP3` проверяются магия, две версии шапки, число анимаций,
  границы данных кадров и типы fp32/i16. Синтетические тесты вызывают настоящий
  загрузчик с компактным `.ani` и штатным `ANPK`; реального BR `.ani` в репозитории
  нет, поэтому воспроизведение с ресурсами пользователя требует запуска игры.
* При отсутствии опорного VC-скелета смещения подхода к дверям считываются прямо из
  штатного VC IFP. Для SA-персонажей смещение берётся **только** из собственного
  SA/BR IFP в `custom`, по корневой кости клипа, даже если группа ассоциаций ещё
  не создана. Отсутствующий SA-клип не подменяется VC-анимацией или VC-смещением.
  В `debug.log` выводятся смещения, модель цели и этапы посадки для проверки в игре.
  Если конкретного клипа в IFP нет, посадка прерывается с указанием этапа вместо
  разыменования пустой ассоциации: корректные кадры нельзя восстановить из пустоты.
* Если skinned-модели не хватает VC-тега кости, для обращения к этому узлу
  используется корневой кадр и выводится предупреждение (первые три случая),
  вместо выхода за границы массива. Это защита от краша, а не исправление
  геометрии неполного скелета.
* `player.mod` остаётся запрещённым: известная запись под этим именем — небезопасная
  заглушка. `player.dff` разрешён только после проверки clump/geometry; неверный или
  неполный файл не подменяет модель игры. Для анимаций используется запрашиваемый игрой
  словарь (`ped.ifp` для базового ped-банка), а не `player.ifp`.
* Если модель из архива ссылается и на «свои» текстуры, и на ванильные (например
  `vehiclegrunge256`), ванильную текстуру нужно положить отдельным `.btx` — словарь TXD
  собирается целиком из архива, чужой TXD не подмешивается.
* Стриминг может освободить память модели в любой момент (как и для обычных моделей) —
  при следующем запросе она снова соберётся из архива (конвертация ~2 мс на модель).
* Путь к папке игры с не-ASCII символами на Windows зависит от системной кодировки —
  как и у остальных файлов игры.

## 8. Проверка

`tools/custom-folder-verification` — стенд, который собирается без игры и проверяет
самую рискованную часть: чтение архива и конвертацию контейнеров.

```sh
cd tools/custom-folder-verification
./build.sh
python3 makezip.py /tmp/test_custom.zip /путь/glendale.mod
/home/user/tools/brref/brref /путь/glendale.mod /tmp/ref_glendale.dff   # эталон brconv
./test_custom /tmp/test_custom.zip /tmp/ref_glendale.dff
```

Что проверяется (см. `out_custom_folder.txt`, результат на тестовом `glendale.mod`):

* архив открывается, записи `store` (модель) и `deflate` (текстуры) извлекаются;
* `.mod` опознаётся как контейнер и конвертируется в модель RenderWare:
  1 124 054 → 1 124 026 байт, 16 имён текстур, **побайтово совпадает** с результатом
  оффлайнового конвертера (эталон `ref_glendale.dff`);
* `.btx` (KTX11, RGBA8, мипы) разбирается, мипы на месте, NPOT (33×17) превращается
  в POT (32×16);
* коллизия: синтетические блоки `CLSF` и `CLST` проходят весь путь
  `br::convertClsToCol` → `customcol::ToGameFormat` и читаются обратно так же, как их
  читает игра, — сферы, боксы, вершины (включая отрицательные и fixed-point round trip),
  грани, материалы (неизвестный → default), **границы в обоих порядках следования**;
  мусорные данные не превращаются в файл коллизии;
* нативное чтение модели: `br::understandModInplace` даёт **те же байты**, что и
  обёртка `br::convertModToDff` (и те же счётчики починок), а `.mod` после него
  уже не опознаётся как BR-контейнер — шифрование действительно снято на месте;
* охранник имён: `player` — зарезервирован, `glendale` — нет;
* синтетический старый shim-`.ani` (лишнее слово @+36) корректируется сдвигом
  тела без изменения кадров; стандартный мобильный ANP3 (`имя@+4`, `count@+28`,
  `groupVal@+32`) читается непосредственно без какой-либо перестановки.
* сборка проходит под AddressSanitizer без замечаний (ASAN-прогон того же стенда:
  `g++ -O1 -fsanitize=address … -o /tmp/test_custom_asan`).

Для этих исходников пройдены отдельные тесты логгера и синтетических IFP, а также
проверка синтаксической компиляции изменённых C++ файлов с архивным `librw`.
Полная сборка/линковка игры и запуск с настоящим IFP здесь не проверены: нужны
зависимости графики/звука и игровые ресурсы. В архиве пользователя изменения
шейдеров `librw` отсутствовали в Git-субмодуле; теперь архивный `librw`
поставляется как исходники проекта, иначе сборка не знает `rw::setSunDirection`.

## 9. Как быстро проверить в игре

1. Собрать проект и положить `custom/*.zip` либо отдельный `custom/ped.ifp` в папку игры.
2. Запустить игру (переменная `REVC_CUSTOM_LOG` не нужна).
3. В `debug.log` должна появиться строка `==== custom folder: custom`, сводка
   `scan: ... .ifp/.ani ...` и записи о загруженных/отвергнутых файлах.
4. Для IFP проверьте `... in parallel bank sa_ped; native VC dictionary kept` и
   `native VC block loaded; building groups`. VC-пед должен пользоваться штатной
   анимацией, SA-пед — только анимацией из `custom`. Для моделей сравните вид в игре
   с моделью из архива.

## 2. Что ещё кладут архивы (дополнение): обычные `.dff`/`.txd`/`.col`, скины, `data/`

Архивы в `custom` могут держать не только BR-контейнеры — игра понимает всё вперемешку,
в любых архивах и подпапках:

| файл в архиве | как игра его понимает |
|---|---|
| `X.mod` | BR-модель (TEA-расшифровка и починка в памяти, см. выше) |
| `X.dff` | обычная модель RenderWare — читается как есть, тем же загрузчиком игры |
| `X.btx` | BR-текстура (одиночная) |
| `X.txd` | целый текстурный словарь — мержится в слот, то, чего нет в `.btx`, берётся отсюда |
| `X.cls` | BR-коллизия модели |
| `X.col` | обычный `.col`-контейнер (VC `'COLL'` и SA `COL2/COL3` внутри): игра берёт из него блок нужной модели по имени, SA-тела конвертируются |
| `.ifp` / `.ani` | SA/BR `ANP2`/`ANP3` в отдельный банк для SA-скелетов; custom `ANPK` игнорируется, VC-скелеты сохраняют штатный IFP |
| `.bmp`, `.png`/`.jpg` в папке со `skin` в имени | **скины игрока** — попадают в список скинов в меню, применяются через `CPlayerSkin` (`.png`/`.jpg` пока надо переконвертировать в несжатый `.bmp`) |

Приоритет между архивами: у кого новее время изменения файла, тот и выигрывает;
раскладка имен не важна — имя модели/текстуры определяется по имени файла.

### Освещение и небо Black Russia (`data/timecyc.json`)

Если в `custom` (в архиве или папкой) лежит `data/timecyc.json` из common-архива клиента,
игра **заменяет свой TIMECYC.DAT на него**: 4 погоды × суточный цикл, небо, солнце,
туман, дальность прорисовки, вода — всё по значениям клиента. Слоты клиента
(0, 5, 7, 9, 12, 17, 19, 22 часов) разворачиваются в 24 часа с интерполяцией; там, где у
клиента поля нет, остаются значения игры. `data/timecyclePresets/*.json` — серверные
погодные пресеты-события клиента, они в суточный цикл не входят и только пишутся в лог.
`data/weather.json` (снег) логируется. Остальные `data/`-файлы (например, physics)
самостоятельно не подключаются; IDE/IPL-карты — отдельный механизм ниже.

### Новая раскладка: `img/*.img` + ZIP-архивы в `custom/`

```
<каталог игры>/img/objects.img       <каталог игры>/img/objects.dir
<каталог игры>/img/area/extra.img    <каталог игры>/img/area/extra.dir
<каталог игры>/custom/common.zip     maps/IDE/*.ide, maps/Level_*/*.ipl
<каталог игры>/custom/pack1.zip      mesh/*.cls
<каталог игры>/custom/pack2.zip      maps/*.col
```

Полученный файл `reVC.txt` — ZIP с корнем `maps/`: чтобы игра увидела его IDE/IPL,
переименуйте его в `common.zip` и положите в `<каталог игры>/custom/` **без**
перепаковки или изменения вложенных путей. Другие `.zip` в этой папке могут
содержать коллизии; `.txt` автоматически как архив не открывается.

* При первом IPL после штатных IDE/CDIMAGE, **до** `CStreaming::Init`, автоматически
  находятся все IMG из `img/` (включая вложенные папки до 8 уровней). Требуется
  формат **VC/GTA3 IMG v1**: рядом с каждым `.img` обязателен одноимённый `.dir`
  с 32-байтовыми записями. SA IMG v2 со встроенным `VER2` не подходит и явно
  пропускается с сообщением в `debug.log`. Проверяются границы секторов и размеры
  перед передачей штатному загрузчику. Одновременно доступны максимум 256 IMG
  (включая штатные), имя пути IMG — не длиннее 63 байт. Для каждого DFF/TXD
  имя внутри DIR должно совпадать с зарегистрированным в IDE именем модели или
  слотом TXD; незарегистрированные DFF пропускаются. Не требуется писать
  `CDIMAGE` для этих архивов в DAT. IMG обрабатываются в детерминированном
  порядке: при одинаковом имени выигрывает более поздний IMG из `img/`.
  Для больших наборов (в присланном логе — около 28 тысяч TXD) пул имён TXD
  вмещает 32768 записей — предел поля `int16` в модели, **не** память загруженных
  текстур. До обработки IMG резервируются имена из штатных `.DIR`, поэтому
  большое число новых TXD не мешает загрузке базовой игры; при добавлении
  новых IMG TXD оставляется 32 слота для интерфейса и скриптов. При достижении
  этого предела новые IMG TXD пропускаются с числом пропусков в `debug.log`,
  а не вызывают assert.
* В IMG индексируются **только DFF и TXD**. Для статических объектов из
  пользовательских IDE (а также подменённых через `img/` простых объектов с
  единственным LOD) SA DFF читается как RenderWare clump, но **все видимые
  атомики** собираются в один объект VC: трансформации вложенных фреймов
  запекаются в геометрию, сохраняются материалы, UV и цвета. Одиночный атомик
  с единичной матрицей не копируется. Для многокомпонентных DFF необходима
  однократная распаковка нативной D3D9-геометрии в момент загрузки; результаты
  живут только пока модель загружена. Штатные VC DFF с несколькими LOD/вариантами
  повреждения проходят прежним путём. Неподдерживаемые скелетные, слишком
  большие (>65535 вершин / >200000 треугольников после объединения) или
  повреждённые статические clump отклоняются с причиной в `debug.log`, а не
  устанавливаются частично.
* **Текстуры из `.txd`** привязываются при чтении DFF по именам материалов.
  Если `house.dff` есть в одном из подключённых `img/*.img`, а `house.txd` —
  в любом другом IMG из `img/` (или в том же), для `house` берётся именно
  `house.txd`, даже когда в IDE у модели во второй колонке указано другое
  имя TXD. Соответствие определяется до регистрации дополнительных IDE-моделей,
  чтобы не создавать тысячи ненужных словарей для их старых IDE-имён.
  Дубликаты учитывают реальный приоритет IMG: берётся тот одноимённый TXD,
  который выигрывает загрузку среди всех пользовательских IMG. Если пары
  нет, сохраняется исходная привязка из IDE (включая штатные VC
  multi-LOD модели). Имена текстур **внутри** выбранного TXD должны совпадать
  с именами материалов в DFF (регистр несущественен); RenderWare преобразует
  растр под активный рендерер. Внутренний TXD-слот — это только учёт загрузки
  и ссылок, создавать его вручную или менять IDE для пары не нужно. TXD живёт
  по обычным ссылкам на модель, а не закрепляется навсегда. Если тот же объект лежит в ZIP как
  `.mod/.btx`, для зарегистрированного IMG-ресурса используется IMG; кэши
  декодирования ZIP и выгрузка RW-моделей за камерой не меняются. Синтетический
  тест проверяет RW 3.6 DFF, нативную D3D9-геометрию и VC D3D8 TXD, но
  настоящие IMG/ZIP пользователя не приложены — совместимость с ними ещё
  нужно проверить в игре и по `debug.log`.
* Коллизии **не читаются из IMG и не берутся из loose `.col/.cls`**: поиск ведётся
  по `.cls` и `.col` внутри всех ZIP-архивов под `custom/`. И `.cls` (CED2
  `CLST/CLSF`), и `.col` (VC `COLL` либо SA `COL2/COL3`) индексируются по
  **внутреннему имени модели**, даже если файлы одинаково названы в разных
  архивах. Если есть обе коллизии для одной модели, проверенный `.col` имеет
  приоритет; среди архивов одного формата выбирается новейший. После загрузки
  IDE коллизия прикрепляется к созданной модели до IPL, живёт независимо от
  потокового DFF и не расходует кэш `.mod/.btx`. Повреждённые чанки
  отбрасываются перед небезопасным VC-парсером.

### Карты BR: `common.zip`, loose `.ide`/`.ipl`, `br_collision.zip`

* `.ide` и `.ipl` ищутся **во всех подпапках внутри `custom/common.zip`** и рекурсивно
  в самой папке `custom` (до восьми вложенных каталогов). Файл в папке с тем же
  относительным путём заменяет запись архива. Архив с другим именем (например,
  присланный `reVC.txt`) сам по себе не подключает IDE/IPL: его надо поместить
  в `custom` под именем `common.zip` либо распаковать IDE/IPL в `custom/maps/`.
  Загружаются разделы IDE `objs`, `tobj`, `anim` (определения объектов) и IPL
  `inst` (позиция + BR-кватернион + interior). При размещении исходные
  компоненты `rx,ry,rz,rw` сохраняют направление оси: штатный загрузчик VC
  уже задаёт отрицательный угол, как требуется для ориентации IPL в SA.
  Раньше адаптер дополнительно инвертировал ось и разворачивал объекты не
  в ту сторону (в том числе при отрицательном `rw` и наклоне по нескольким
  осям). В `anim` поля после модели —
  **TXD, затем банк анимации**, не наоборот. Анимация SA для такого объекта
  в VC не запускается, но TXD назначается корректно; удвоенное по ошибке имя
  TXD `SM_acc_PlayerBPSM_acc_PlayerBP` из присланной IDE сокращается только
  при точном повторе до `SM_acc_PlayerBP`, остальные длинные имена отклоняются;
  разделы с несовместимой с VC структурой (`occl`, `cull`, `2dfx` и др.) не передаются
  в небезопасные штатные парсеры. `anim` регистрируется как статический объект:
  привязка BR-анимблока к мировой модели ещё не реализована. В корректном файле
  `inst.lod` трактуется как индекс записи **этого** IPL: LOD-модель связывается с
  ближней моделью через механизм больших зданий VC. При повреждённой строке IPL
  связь LOD для всего файла пропускается, чтобы не спутать сдвинутые индексы;
  это не сохраняет все особенности оригинального SA/BR LOD-стриминга. В присланных
  гоночных IPL последнее дробное поле `200.0`/`299.0` — дальность, а не LOD-индекс;
  оно не образует ложной связи с записью номер 200 или 299. В IDE число сеток
  `1..3` читается отдельно от дистанций/флагов. Повторное использование ID
  различными именами IDE не удаляет старую модель: размещение ищется по имени.
  Точно совпадающие модель, интерьер, координаты и поворот из нескольких IPL
  размещаются один раз (без потери других позиций и вариантов поворота).
* Если альтернативные IPL (ивенты, гонки, старая растительность) **не должны**
  загружаться одновременно, создайте `custom/active_ipl.txt` со списком активных
  *полных относительных путей* внутри `common.zip`, по одному на строку, например
  `maps/Level_Town/Level_Arzamas_N.ipl` для архива с путями `maps/...`.
  Регистр/разделители пути не важны; пустые строки и комментарии `#`/`//` допустимы.
  В игровом логе найдено по две копии многих файлов в `data/maps/...` и `maps/...`:
  **побайтово одинаковые** копии с одним путём без начального `data/` читаются
  один раз, а отличающиеся по содержимому остаются разными вариантами с
  предупреждением в `debug.log`. Полные исходные пути работают в списке IPL;
  ни один отличающийся вариант загрузчик не выбирает автоматически.
  Наличие файла включает режим списка: непрописанные IPL не загружаются, IDE при
  этом по-прежнему индексируются все. Пустой список не загружает ни одного BR IPL;
  если файла нет, как раньше, загружаются все IPL (кроме точных дублей). Неизвестные
  пути и невалидные строки видны в `debug.log` — это не автоматический выбор версии
  карты; какой набор нужен, определяет автор карты/пользователь. В исходном
  `Level_Other/Level_South.ipl` остались маркеры конфликта слияния: загрузчик не
  может выбрать правильную ветку. Точные повторы удаляются, но автору карты
  следует разрешить конфликт; необратимо повреждённые числа отклоняются.
* Дополнительные IDE загружаются после штатных IDE и **до** `CStreaming::Init`;
  коллизии устанавливаются до создания экземпляров, а дополнительные IPL читаются
  после штатных IPL. Исходные BR ID (например, 42927) переводятся в свободные индексы
  reVC `<32768` (поле `CEntity::m_modelIndex` — `int16`). Отсутствующие файлы моделей
  и позиции за границами игровой сетки пропускаются с итоговым счётчиком в `debug.log`.
  Для полного набора карт увеличены слоты моделей и коллизий и сетка секторов
  до ±4000. Пулы зданий и ссылок на сектора **расширяются блоками по мере нужды**
  без перемещения ранее созданных объектов; IPL больше не ограничивается 50 тыс.
  зданиями/300 тыс. ссылками. Остаются физическая память, диапазон игровых
  дескрипторов (до ~8 млн слотов) и проверка границ мира; при неудаче выделения
  запись пропускается и это видно в `debug.log`. **Лимиты LRU-кэшей не увеличены**.
  Ближние RW-объекты выгружаются штатным стримингом; дальние BR LOD (особый список зданий VC)
  дополнительно освобождают свои RW-клоны вне обзора при нехватке памяти, а
  модели остаются доступными для штатного вытеснения.
* `.cls` в `custom/br_collision.zip` и других ZIP — это **контейнеры из многих моделей**, а не
  один `.cls` на модель. Индексируются **внутренние имена** чанков `CLST`/`CLSF` с
  `CED2`; архив распаковывается по одному файлу, не хранится целиком в памяти.
  Блок с проверенными границами, смещениями, вершинами int16/128 и гранями
  переводится в VC `COLL` и присоединяется к соответствующей IDE-модели.
  Для массивов A/B используются 20-/28-байтные сферы/боксы SA, незнакомые
  варианты/битые чанки пропускаются. Коллизия не зависит от времени жизни
  RenderWare-модели и сохраняется при её штатном вытеснении.

**Проверка:** синтетические тесты проверяют DIR/VC COLL/IDE/IPL/CLST/CLSF,
вложенные ZIP, расширение пулов и выбор IPL; отдельный тест сверяет итоговые
матрицы librw с SA на строках из архива (включая отрицательный `rw` и 3D-наклон).
Присланный архив с 71 IDE и 82 IPL
дополнительно прочитан тем же парсером: 26 725 записей IDE без отказов;
129 918 записей IPL приняты, 5 повреждённых строк остаются отвергнутыми
(3 маркера конфликта, одна оборванная строка и один испорченный кватернион).
Найдено 13 207 точных повторных размещений среди определённых моделей.
В присланном затем игровом `debug.log` (merge ревизии `91e8f54`) смонтированы
шесть IMG, зарегистрированы 26 484 модели, размещены 113 538 объектов, **0
ошибок ёмкости**. Однако IDE/IPL там прочитаны из двух параллельных деревьев
`data/maps/` и `maps/`; далее возник `CPedPool::GetJustIndex` assertion на
недействительном/освобождённом слоте педа. Лог не содержит стека вызовов
этого assert и не доказывает, что падение вызвано картой или строкой
генератора машин непосредственно перед ним. Новую защиту валидности педов
и пропуск точных алиасов нужно проверить в игре; исправление ориентации
проверено на матрицах, но внешний вид конкретных объектов по-прежнему
требует проверки в игре по координатам/скриншотам.

### Debug-лог (`debug.log`)

Один `debug.log` содержит скан папки `custom`, загрузку IMG/TXD/IFP, причины отказов и,
при пойманном падении, строки `CRASH: ...` (сигнал/исключение + backtrace на Linux).
При старте новой сессии файл создаётся заново, предыдущий лог перезаписывается.
При ошибке TXD лог указывает IMG, сектор, размер и первые байты заголовка — это помогает
отличить отсутствие архива от файла неподходящего формата. Учитывайте, что не всякое
аварийное завершение ОС позволяет выполнить обработчик.

## 3. SA-модели и отдельный animation bank

Компактный SA `ped.ifp` (`ANP2`/`ANP3`; в том числе size-less SA-mobile ANP3) загружается
в дополнительный блок `sa_ped`, а штатный VC `ped`-блок остаётся доступен и не подменяется.
При потоковой загрузке остальных словарей создаются отдельные `sa_<имя>` блоки. Для
ассоциаций SA-модели разрешаются SA-иерархии и явные алиасы из дополнительных SA IFP-банков
(включая fighting, weapons, car и bike clips); иерархия VC никогда не подставляется в SA
clump. Если подходящего SA-клипа нет, позиция пропускается и записывается в `debug.log`.
Нативные VC-модели продолжают использовать только исходные VC association groups.
Активные ассоциации удерживают ссылки на нужные animation banks до завершения.
Чтобы использовать соответствующие действия, поместите в `custom` оригинальные SA IFP
(если они входят в ваш легальный набор ресурсов): `MELEE_1`, `FIGHT_E`, `BBBAT_1`,
`GCLUB_1`, `KNIFE_1`, `CSAW_1`, `GRENADE`, `UZI`, `RIFLE`, `COLT45`, `SUNBATHE`, `FAT`,
`STDCARAMIMS`, `LOWCARAMIMS`, `VANCARANIMS`, `COACHCARANIMS`, `SPORTBIKEANIMS`,
`VESPABIKEANIMS`, `HARLEYBIKEANIMS`, `DIRTBIKEANIMS`, `BIKES`, `BIKEV`, `BIKEH` и
`BIKED`. Они читаются как отдельные SA-банки; отсутствующие файлы просто не загружаются.
Одного `ped.ifp` недостаточно для стрельбы SA-педа: при отсутствии подходящего
оружейного IFP/ANI атака отменяется с предупреждением `Weapon animation unavailable`
(в логе указаны модель, тип оружия, группа и ID клипа), а не использует VC-анимацию.

`CPedModelInfo` распознаёт SA-совместимый скин по его skinned HAnim hierarchy и ключевым
bone tags. Таблица позиций костей выделяется по числу костей скелета (не ограничена старым
VC-буфером на 64 элемента). Для такого clump `CPed` выбирает SA association bank; нативные VC
clumps продолжают выбирать оригинальные VC associations. Поэтому замена только текстурой не
включает SA-движения, а настоящий SA `player.dff` должен содержать skinned SA skeleton.
Обычный пользовательский VC `.ifp` по-прежнему загружается в штатный блок.
Ассоциация для каждого педа теперь строит массив узлов под **его собственный** скелет:
число и порядок костей у пользовательского DFF могут отличаться от опорного `cop`.
Иначе рендер анимации проходит за пределы массива узлов; при несовпадении размеров
`debug.log` пишет `anim assoc: ... reference=... frames, target=...`. Для ассоциаций,
созданных другими путями (например катсценой), перед обновлением также проверяется число
узлов и при необходимости восстанавливается соответствие костей.

Формат BR `.ani` определяется по магии, а не по расширению: мобильный ANP3 из
архивов сразу проходит компактный путь, а у старого shim-варианта удаляется
лишнее слово перед первым клипом. Для сборок без `ANIM_COMPRESSION` сжатые SA keyframes разворачиваются перед
обычной обработкой. Парсер проверяет структуру и границы кадров; полноценный runtime-тест
с настоящим SA DFF/IFP нужно выполнять на установленной игре с соответствующими ресурсами.

## 4. Скины из BR-паков (.btx)

Архив с `skin` в имени (например `br_tex_skins_01.astc.zip`) индексируется как источник
скинов игрока: каждый `.btx` из него появляется в меню скинов и применяется напрямую
(BR-текстура декодируется в память и становится текстурой игрока). Обычные `.bmp`-скины
продолжают работать как раньше.

## 5. «Тихие» краши: почему в debug.log не было строки CRASH, и что изменится

Кейс из второй пары логов: игра запускалась, работала минуты, стримила мир — и умирала
без единой строки `CRASH`. Причина нашлась в точке входа: в Windows-сборке игру стартует
`WinMain` из `src/skel/win/win.cpp`, а регистрация обработчиков краша (`DebugLogInit`)
стояла в `main()` из `src/core/main.cpp` — который в этом порту **не вызывается вовсе**.
Лог при этом мог писаться, поэтому казалось, что обработчики уже подключены. Теперь
`WinMain` открывает единый `debug.log` **до** регистрации обработчиков;
`DebugLogInit()` также идемпотентно вызывается при запуске движка и первой записи
из custom-подсистемы. Обработчики пишут в уже открытый файловый дескриптор,
не создавая второй файл. Отдельный тест проверяет запись CRASH-строки тем же
дескриптором; реальное падение в работающей игре этим тестом не имитируется.

Главный подозреваемый самого краша тоже найден и закрыт: в архивах клиента часть
моделей — **пустые заглушки** (clump на ~200–1200 байт: `rocketla` — 192 байта,
`seaspar` — 1186 байт: без атомиков или с пустой geometry — клиент так хранит
неиспользуемое оружие/транспорт). Раньше они проходили проверку «это clump» и отдавались
игре, а игра падала позже, когда модель стримила/использовала — без внятного следа.
Теперь перед выдачей игре модель проверяется структурно (`validateClumpForGame`):
корень-clump, есть хотя бы одна непустая geometry с материалами, объявленные данные
помещаются в файл (понимаются оба расклада: geometry внутри atomic и старый BR-расклад
с GEOMLIST уровня clump). Заглушка/обрезанный файл бракуется с записью в лог:

```
model rocketla: not usable as a game model (the model holds no geometry - an empty model stub), the game's own file is used
```

и вместо неё работает собственная модель игры. Дополнительно на MSVC чтение модели и
сборка текстуры обёрнуты в SEH-страховку: даже если что-то проскочит мимо проверок,
в лог уйдёт `the load crashed (exception 0x...), the game's own file is used`, а игра
продолжит работать.

Стенды: `tools/custom-folder-verification/test_validate` проверяет синтетические
заглушки, обрезанные модели и native-geometry; отдельные `tests/DebugLogTests.cpp`
и `tests/CustomIfpTests.cpp` проверяют единый лог и повреждённые VC/SA IFP.
Реальный `glendale.mod` и реальные IFP нужны для дополнительного прогона в игре.
