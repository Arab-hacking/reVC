# Крепление и снятие деталей тюнинга в клиенте

Снято с `libblackrussia-client.so` (35 067 024 Б, md5 `3c003ac47dda1b2857eacbfcd02cc70d`),
AArch64. Дополняет главу 04 (`04-цвета-и-тюнинг.md`), где этих двух функций нет.

## 1. Что оказалось не так в прошлой записи

В главе 04 `0x17f67ec` назван `GetFirstAtomic`, а про вызовы сказано «ноль `bl`».
Проверка по всей `.text` это подтверждает: **прямых `bl` на `0x17f67ec` нет**. Но
`0x17f7830` заканчивается *хвостовым* переходом:

```
0x017f7cc8  ldp x20, x19, [sp, #0x180]
...
0x017f7ce4  add sp, sp, #0x190
0x017f7ce8  b   #0x17f67ec        ; tail call, не bl
```

`b`, а не `bl` — поэтому поиск по `bl` его и не нашёл. Аргументы перед переходом:
`x0 = x20` (компонент), `x1 = [sp+0x38]` (машина).

## 2. `0x17f7830` — это `RemoveFromVehicle`, а не крепление

Три расшифрованные строки функции (ключи из `.rodata`):

| адрес шифра | ключ | строка |
|---|---|---|
| `0x4ed93d` | `0x3e4c48` (8 Б) | `Trying to remove missing component Id %u slot %` |
| `0x4ed97c` | `0x3fc2b0` (8 Б) | `Can't remove component Id %u slot %u vehicle id %u` |
| `0x4ed9af` | `0x3ed148` (8 Б) | `Wrong position type %d, for dummy %s` |

Формат третьей строки совпадает со строкой 1197 в главе 04, но там она приписана
тюнингу вообще; здесь видно, кто её зовёт и с какими аргументами.

Что функция делает по коду:

```
0x017f786c  ldr  w1, [x0, #8]        ; X0 = компонент, +0x08 = m_slot
0x017f7870  mov  x0, x9              ; X1 = машина
0x017f7878  bl   #0x180d48c          ; FindBySlot(vehicle, slot)
0x017f7880  cbz  x0 -> 0x17f7998     ; не нашли -> ветка «missing component»
0x017f7884  ldr  x8, [x0, #0x28]     ; узел+0x28 = привязанный атомик
0x017f788c  cmp  x8, x20             ; тот ли это компонент
0x017f7890  b.ne #0x17f7adc          ; нет -> выход
0x017f7894  ldrb w8, [x20, #0x40]    ; компонент+0x40 = bool
0x017f7898  tbnz w8, #0, 0x17f7cb0   ; флаг стоит -> tail call GetFirstAtomic
0x017f78a8  bl   #0x180d66c          ; иначе сдвиг массива узлов (erase)
```

`0x180d66c` — это `erase` из массива узлов шагом `0x38`
(`stp q2,q0,[x8,#0x10]; str q1,[x8]; str x10,[x8,#0x30]` — переносит 0x38 байт
следующего узла на место текущего). То есть функция **снимает** деталь с машины.

Отсюда же становится понятен флаг `+0x40`: если он стоит, деталь не стирается из
массива, а уходит в `0x17f67ec` — то есть остаётся, но перестаёт быть видимой.
Это ровно тот `w7` конструктора, который `AddWheelUpgrade` передаёт как **1**
(`0x17fac30  mov w7, #1`), а загрузчик `carmods.dat` — как **0**
(`0x17fc1dc  mov w7, wzr`).

## 3. `0x17f67ec` — `GetFirstAtomic(clump, atomicType)`

Второй аргумент — **тип атомика**, и функция перебирает кламп в поисках нужного:

```
0x017f681c  ldr  w8, [x0, #8]      ; x0 = компонент (или узел), +0x08 = слот
0x017f6828  bl   #0x180d48c        ; FindBySlot
0x017f6830  ldp  x25, x23, [x0, #8]   ; узел+0x08, узел+0x10
0x017f6838  ldp  x22, x21, [x0, #0x18] ; узел+0x18, узел+0x20
0x017f6840  bl   #0x180d66c        ; erase
0x017f6844  ldr  x0, [x19, #0x68]  ; машина+0x68 = RwObject
```

Дальше четыре одинаковых блока. Каждый:

1. `bl 0x15b45f0` с `w1 = 2`, `3`, `4`, `5` — достаёт из `RwObject` объект по типу
   (по коду это последовательные обращения к списку `RwObject`; `0x15b45f0` берёт
   `[x0,#8]` и ищет запись с заданным ключом);
2. `0x1721b14` — «первый элемент списка» (`ldr x8,[x0,#0x20]!`, `sub x9,x8,#0x10`),
   `0x1721abc` — «следующий» (`adr x1,` + `bl 0x155388c`);
3. `bl 0x1551a3c` и `strb #4, [x0,#2]` — переключение чего-то в найденном объекте;
4. `bl 0x15b36a0` — уменьшение счётчика ссылок (`ldrh w8,[x0,#0x34]; sub w8,w8,#1`).

Итого функция не «берёт первый атомик», а **снимает владение с четырёх объектов
машины по типам 2..5** и удаляет узел из массива. Название `GetFirstAtomic` из
главы 04 для неё неверно: это ближе к «освободить занятые слоты под деталь».

## 4. `0x180d6e4` — обёртка над всем набором слотов машины

```
0x0180d704  bl   #0x17f61f4        ; аксессор пула
0x0180d710  bl   #0x17fa99c        ; собрать слоты машины
0x0180d714  ldr  x8, [x19, #0x490] ; машина+0x490
0x0180d718  ldr  x9, [x19, #0x488] ; машина+0x488
0x0180d720  b.eq #0x180d860        ; пусто -> выход
0x0180d738  mul  x23, x8, x9       ; шаг 0x38
0x0180d84c  bl   #0x17fa790        ; AddToVehicle по каждому слоту
0x0180d870  bl   #0xbc7e9c         ; освобождение временного массива
```

То есть `0x180d6e4` — «применить/снять все детали машины», а `0x17fa790` —
`AddToVehicle(const CCarModComponent&, CVehicle&, bool)`.

## 5. Что из этого следует для порта

`AddToVehicle` (`0x17fa790`) — тонкая функция: она проверяет слот и зовёт
`0x17f7830`. Вся работа с клампом и атомиками лежит **не в ней**, а в
`0x17f67ec`, и это снятие владения, а не привязка готового атомика к кадру.

Поэтому в порте `CCarModComponentPool::AddToVehicle` остаётся тем, что он есть:
проверка слота и учёт. Визуальное крепление детали — отдельная задача, и она
требует разбора того, как клиент строит узел `0x78` байт (`+0x18`, `+0x38`,
`+0x40` — RwFrame/RwMatrix/атомик) и откуда берётся клонированный атомик модели
детали. В главе 04 и в этой записи этого ещё нет.
